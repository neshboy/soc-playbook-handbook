# Windows Event IDs: Account & Group Management Events

This cluster covers the events that fire when identities and group memberships change on Windows: account lifecycle (create, enable, disable, delete, password reset), group membership changes (global and local security groups), and the audit policy event that tells you someone tried to turn the cameras off before doing any of the above.

All events here live in the **Security** log, generated by Advanced Audit Policy subcategories **Account Management** and **Policy Change**. If those subcategories aren't enabled with Success and Failure auditing on your DCs and member servers, you simply won't see them - check the GPO before assuming an attacker "somehow avoided logging."

**[MANAGEMENT]** - Account and group management auditing on domain controllers is one of the highest-value, lowest-noise audit categories you can turn on. Confirm it's enabled via Default Domain Controllers Policy (or an equivalent baseline GPO) and revisit it during every audit cycle - it's a common casualty of GPO drift.

---

## 4719 - System Audit Policy Was Changed

**Plain terms:** somebody changed what gets audited. This is disproportionately important because an attacker who disables a subcategory - say, Account Management or Logon/Logoff auditing - doesn't need to clear the log (loud, see 1102 elsewhere in this book) if they can just make sure nothing gets written to it in the first place.

**Where it appears:** Security log, any host where `auditpol.exe` or a GPO push modifies the local effective audit policy - but the events that matter most come from domain controllers and Tier 0 servers.

**Key fields:**

| Field | Meaning |
|---|---|
| Subject | Account that made the change |
| Subcategory | Which audit subcategory was altered (e.g., "Security Group Management") |
| Subcategory GUID | Stable identifier for the subcategory |
| Changes | Old setting vs. new setting (audit success/failure enabled or disabled) |

**Normal:** rare. Shows up during initial hardening, GPO baseline pushes, or when a security engineer is deliberately tuning audit scope. It should correlate to a known change ticket.

**Suspicious:** any 4719 on a DC, Tier 0 asset, or server outside a scheduled change window - especially one disabling Success/Failure auditing on "Account Management," "Logon/Logoff," "Object Access," or "Detailed Tracking." Also watch for 4719 immediately followed by account or group manipulation events (4720, 4728, 4732, etc.) from the same Subject - the classic "blind the log, do the thing" pattern. A careful attacker restores the prior setting with a second 4719 shortly after, so a clean current-state policy isn't proof nothing happened.

**Correlate with:** 1102 (log cleared - the clumsier version of this), any subsequent 4720/4722/4724/4725/4726/4728/4729/4732/4733/4738, and 4688 for the process that invoked `auditpol.exe`.

**Common false positives:** GPO refresh cycles (every 90 minutes by default) replay 4719 events with no real change - dedupe on identical old/new values. Security tooling deployments (SIEM agents, EDR onboarding) also touch audit policy during setup.

**Analyst note (informal):** don't chase every 4719 - on a live domain there's a background hum of these from policy refresh. Hunt for a *value change*, not just the event occuring.

```kusto
// KQL - Microsoft Sentinel: audit policy changes outside change windows, DCs only
SecurityEvent
| where EventID == 4719
| where Computer has_any ("DC01", "DC02") // adjust to your DC list or a watchlist
| project TimeGenerated, Computer, SubjectUserName, SubjectDomainName,
          AuditPolicyChanges, SubCategory = tostring(EventData)
| order by TimeGenerated desc
```

## Account Lifecycle Events: 4720, 4722, 4723, 4724, 4725, 4726

These six form the life story of a local or domain user account: created, enabled, password touched (by self or someone else), disabled, deleted. Individually mundane. In sequence - especially alongside group membership changes - they tell you whether you're looking at a routine joiner/mover/leaver process or a staged account being built and torn down around an intrusion.

**Shared fields across this group:**

| Field | Meaning |
|---|---|
| Target Account Name / SID / Domain | The account being acted upon |
| Subject (Account Name / SID / Logon ID) | Who performed the action |
| Additional Information / Privileges | Present on some variants, usually blank for these |

### 4720 - A user account was created

New account, plain and simple. **Normal:** IT onboarding via approved provisioning tooling, an HR-integrated joiner workflow, or an admin manual create tied to a ticket - Subject is almost always a known helpdesk/IT admin or provisioning service account. **Suspicious:** creation by an account that's never created a user before, creation outside business hours, creation from a workstation rather than a DC/admin tooling path, or a naming convention that breaks your org's standard (e.g., `svc_backup01` pattern violated by `admin_temp1`).

### 4722 - A user account was enabled

Often rides alongside 4720 for brand-new accounts, but watch for it appearing **alone**, re-enabling a previously disabled account - a service account, a departed-employee account, or a built-in account. Re-enabling a dormant account with existing group memberships is a faster path to privilege than creating a new one, and it skips the "new account" tripwire some detections rely on.

### 4723 - Password change attempt (self-service)

The account holder changed their own password - authenticated as themselves, used the "change password" flow, not an admin reset. **Normal:** routine expiry cycles, post-phishing-scare changes, self-service portal use. **Suspicious:** 4723 immediately following a suspicious 4624/4648 logon, or a burst of these for the same account in a short window (could be a user racing an attacker for control, or credential-stuffing tooling that also attempts a password change).

### 4724 - Password reset attempt (by someone else)

An admin (or an account with delegated reset rights) reset *someone else's* password. This is the one to care about far more than 4723 - attackers use it to hijack an account without ever knowing the original password. **Suspicious:** targeting a privileged account by a Subject outside the identity team; a reset immediately preceding a logon (4624/4648) for the same target from an unfamiliar source; helpdesk-tier accounts resetting passwords far outside their delegated OU. This is also a classic post-Kerberoasting/credential-theft pivot - reset a higher-value account rather than crack its hash.

**[ANALYST]** - When you see 4724, ask three things: is it tied to an open ticket, does the Subject's delegation actually cover this OU/account, and did a logon follow shortly after from a host/IP the target doesn't normally use. Three "no" answers is a hands-on-keyboard takeover, not noise.

### 4725 - A user account was disabled

**Normal:** offboarding, contractor end-date automation, or the SOC disabling a compromised account during containment (a *good* 4725 you'll generate yourself). **Suspicious:** disabling by someone outside the offboarding process, especially of a monitoring or logging service account - a quiet way to stall a detection pipeline without ever touching the audit policy.

### 4726 - A user account was deleted

**Suspicious:** deletion shortly after creation (a throwaway staging account cleaned up to reduce forensic footprint), deletion of an account recently pulled from a privileged group (4732 → 4733 → 4726 is a tight cleanup pattern worth its own rule), or deletion outside the offboarding process.

**Common false positives across 4720-4726:** identity governance tooling (SailPoint, Saviynt, native AD sync jobs) doing bulk joiner/mover/leaver work generates legitimate bursts - baseline those service accounts so they don't drown out anomalous human activity.

```kusto
// KQL - full account lifecycle timeline for a single target account
SecurityEvent
| where EventID in (4720, 4722, 4723, 4724, 4725, 4726)
| where TargetUserName == "j.alvarez" // swap for the account under investigation
| project TimeGenerated, EventID, Activity, TargetUserName, SubjectUserName,
          SubjectDomainName, Computer
| order by TimeGenerated asc
```

```spl
`` SPL - Splunk: admin-initiated password resets (4724) targeting privileged group members ``
index=wineventlog EventCode=4724
| lookup privileged_accounts.csv Target_Account_Name OUTPUT is_privileged
| where is_privileged=1
| table _time, Target_Account_Name, Subject_Account_Name, Computer
| sort - _time
```

## Security Group Membership Events: 4728, 4729, 4732, 4733

Windows has two flavors of security groups relevant here: **global** groups (domain-wide scope, used for role-based grouping like "Finance-Users") and **local** groups (scoped to a single machine, or the domain's built-in local groups like **Administrators**, **Backup Operators**, **Remote Desktop Users**). Which event you get depends on which kind of group was touched, not where the action happened.

| Event ID | Meaning |
|---|---|
| 4728 | Member added to a security-enabled **global** group |
| 4729 | Member removed from a security-enabled **global** group |
| 4732 | Member added to a security-enabled **local** group |
| 4733 | Member removed from a security-enabled **local** group |

**Key fields (all four):**

| Field | Meaning |
|---|---|
| Member Name / SID | The account (or group, for nested membership) being added/removed |
| Group Name / SID | The group being modified |
| Subject | Who made the change |

**Normal:** access requests through an approved workflow (ITSM ticket → identity team adds user → automatic removal at project end), group nesting changes during org restructuring, HR-driven role changes.

**Suspicious:**
- Any 4732 adding a member to local **Administrators** on a server that isn't a designated admin workstation or jump host.
- 4728 adding a member to **Domain Admins**, **Enterprise Admins**, **Schema Admins**, or any Tier 0 group, especially by a Subject that isn't a break-glass or identity-team account.
- Self-addition - Subject and Member being the same account is almost never legitimate for privileged groups.
- Add followed by a short-lived removal (4728/4732 then 4729/4733 within minutes to hours) - "borrow the privilege, use it, put it back" reduces dwell time and evades access reviews that only sample current state.
- Additions to **Remote Desktop Users**, **Remote Management Users**, or **Backup Operators** (the last is functionally admin-equivalent via backup/restore rights, and underwatched next to Administrators and Domain Admins).

**Correlate with:** 4720/4722 (freshly created/re-enabled account getting privileged access immediately?), 4738 (attribute changes bundled with the membership change), 4672 (did the account then exercise those special privileges?), 4624/4648 (logons by the newly privileged account to new destinations), and 4719 if the sequence started with an audit policy change.

**[STAKEHOLDER]** - "Somebody made a mistake in Active Directory" and "somebody just gave an attacker the keys" look identical on paper. The risk isn't the event, it's the gap before someone notices - real-time alerting on Tier 0 groups and periodic access review both matter; one catches what the other misses.

**[MANAGEMENT]** - Privileged group changes should page someone, not sit in a daily digest. Set an SLA (commonly under 15 minutes to acknowledge, under 1 hour to confirm legitimacy against a change ticket) and review the "privileged groups" list quarterly - it drifts as new tooling introduces powerful groups nobody classified.

**Common false positives:** endpoint management tooling and PAM/JIT solutions that grant and revoke local admin dynamically generate legitimate add/remove pairs at high frequency - exactly the pattern flagged above. Allow-list those service accounts explicitly or every shift drowns in noise.

```spl
`` SPL - Splunk: additions to Tier 0 groups by non-approved subjects ``
index=wineventlog (EventCode=4728 OR EventCode=4732)
| lookup tier0_groups.csv Group_Name OUTPUT is_tier0
| where is_tier0=1
| lookup approved_identity_admins.csv Subject_Account_Name OUTPUT is_approved
| where isnull(is_approved)
| table _time, EventCode, Group_Name, Member_Name, Subject_Account_Name, Computer
```

```kusto
// KQL - "borrowed privilege" pattern: add then remove from same group within 4 hours
let adds = SecurityEvent
| where EventID in (4728, 4732)
| project AddTime = TimeGenerated, Member = MemberName, Group = TargetUserName, AddSubject = SubjectUserName;
let removes = SecurityEvent
| where EventID in (4729, 4733)
| project RemoveTime = TimeGenerated, Member = MemberName, Group = TargetUserName;
adds
| join kind=inner removes on Member, Group
| where RemoveTime - AddTime < 4h
| project AddTime, RemoveTime, Member, Group, AddSubject
```

## 4738 - A User Account Was Changed

The catch-all event for account attribute modifications. Genuinely tedious to triage, because "user account changed" covers everything from a helpdesk agent fixing a typo in a display name to an attacker adding a Service Principal Name (SPN) to enable a targeted Kerberoasting request, flipping the "password never expires" flag, or clearing "smart card required" to open up password-based auth on an account meant to be smart-card-only.

**Key field to actually look at:** **Changed Attributes**. The event fires on nearly any modification, so the header fields alone (Target Account, Subject) tell you almost nothing - you have to read what changed.

**Normal:** display name, description, office/phone/manager edits from HR sync or self-service profile updates; routine UAC (User Account Control flag) toggling during legitimate maintenance.

**Suspicious:**
- **ServicePrincipalName** added to an account that didn't have one - classic setup before a Kerberoasting-style service ticket request (see 4769 with RC4 encryption, covered elsewhere in this book).
- **UserAccountControl** changes adding `DONT_EXPIRE_PASSWORD`, removing `SMARTCARD_REQUIRED`, or adding `TRUSTED_FOR_DELEGATION` / `TRUSTED_TO_AUTH_FOR_DELEGATION` - all weaken the account's posture quietly and persistently.
- **primaryGroupID** changes - a lesser-known escalation trick, since some tools don't check primary group the way they check explicit membership.
- Any 4738 on a privileged account by a Subject outside the identity team, especially clustered with a 4724 or 4728/4732 in the same session.

**Common false positives:** the single noisiest event in this cluster - HR-to-AD sync connectors, self-service profile updates, and routine helpdesk edits fire it constantly. Don't alert on raw volume; alert on specific attribute changes.

**[ENGINEERING]** - Filter on Changed Attributes, not the event ID alone. Confirm how your pipeline (Sentinel's SecurityEvent table, a Splunk TA, Elastic's winlogbeat module) breaks out that field before writing a detection - a naive "EventID=4738" rule with no attribute filter buries the SOC in noise inside a day.

```spl
`` SPL - Splunk: 4738 events where SPN or delegation-related UAC flags changed ``
index=wineventlog EventCode=4738
| rex field=Message "Attribute Edited:\s*(?<changed_attrs>[^\r\n]+(\r?\n\s+\S+)*)"
| where match(changed_attrs, "(?i)serviceprincipalname") OR match(changed_attrs, "(?i)trusted.*delegation")
| table _time, Target_Account_Name, Subject_Account_Name, changed_attrs, Computer
```

## Example Investigation Narrative

**Alert:** SIEM correlation rule fires on "privileged group membership change followed by password reset," triggered by a 4732 (add to local Administrators on `FS-PAYROLL01`) followed nine minutes later by a 4724 targeting the same account.

**Analyst walkthrough:**

1. Pull the raw events. 4732: `Member Name = svc_reporting`, `Group Name = Administrators`, `Subject = j.chen`. 4724: `Target Account = svc_reporting`, `Subject = j.chen`.
2. Check whether `j.chen` has delegated rights over `FS-PAYROLL01`'s local groups. Ticketing search turns up nothing for the past 30 days - unusual, since routine access grants normally carry a change ticket.
3. Pull `j.chen`'s recent logon history. A 4648 (explicit credential logon) from their own workstation to `FS-PAYROLL01` lands eleven minutes before the 4732, authenticating via NTLM rather than the Kerberos they normally use - worth flagging, not conclusive alone (NTLM fallback happens for mundane reasons too).
4. Check `j.chen`'s own account for compromise signs - recent 4625 failures preceding a success, unfamiliar source IP. Turns out their laptop had a phishing click reported to the helpdesk two days prior that never got escalated to the SOC.
5. Escalate: a compromised helpdesk-tier credential planting persistent access on a payroll server via a service account, then resetting its password to complete the takeover. Contain `j.chen`'s account, disable `svc_reporting`, and pull `FS-PAYROLL01`'s 4688 history for the reset window.

**Closure note:** this one ends as a True Positive, escalated to a full incident - but it's worth stating plainly for the playbook - plenty of investigations that start with this exact signature (privileged add + reset) end in **Benign Positive**, because a legitimate emergency access grant skipped the ticketing step during an outage. Don't let the shape of the pattern substitute for actually checking the ticket queue, the delegation model, and the Subject's own logon integrity before you write "malicious" in the case notes.

## Correlation Cheat Sheet

| If you see... | Also pull... | Why |
|---|---|---|
| 4719 | 4720-4738 range, 1102, 4688 for auditpol.exe | Was logging weakened right before manipulation? |
| 4720/4722 | 4728/4732 shortly after | New account immediately granted group access? |
| 4724 | 4624/4648 for the target account | Reset followed by a logon from an unfamiliar source? |
| 4725/4726 | 4729/4733 preceding it | Cleanup pattern - remove from group, then disable/delete |
| 4728/4732 | 4672, 4624 for the member account | Was the new privilege actually exercised? |
| 4738 | 4769 (RC4 service tickets), subsequent 4624 | SPN/UAC flag change enabling a follow-on attack path |

Building detections off single events in this cluster will always be noisier than building them off the sequence. A 4732 alone is Tuesday. A 4732 on a Tier 0 group, by a Subject with no matching ticket, nine minutes after a suspicious logon, is the version worth waking someone up for.
