# Playbook Coverage Matrix

One row per playbook, keyed on the new canonical ID from `PLAYBOOK-ID-MIGRATION-MAP.md`. "Threat" is a one-line statement of what the playbook is actually watching for. "Stakeholder" is the business-side audience/decision-owner named in the playbook's own `[STAKEHOLDER]` business-risk framing (who cares if this goes wrong); "Response Owner" is who actually drives triage/containment (defaults to SOC Tier 1/Tier 2 escalating up the standard ladder — Tier 1 → Tier 2 → Tier 3/SOC Manager → Client/CISO — per `TERMINOLOGY-STANDARD.md`, with the named specialist team where the playbook calls one out explicitly). ATT&CK codes are the primary techniques mapped in each file, not an exhaustive list.

## Coverage Gaps & Near-Duplicates

**Total rows: 160** (156 category playbooks + 4 master playbooks).

### Categories that look thin relative to their real-world attack surface

- **Insider Threat (12 playbooks)** is the smallest category in the book by playbook count, yet insider risk in practice spans far more scenarios than are covered here — there is no dedicated playbook for collusion/fraud rings, sabotage of production systems or industrial/OT processes, or "shadow IT" (an employee standing up an unsanctioned SaaS tool that quietly becomes a data store). All twelve current entries are variants of "an insider moved or destroyed data"; none addresses an insider *degrading availability or integrity* of a live production system short of data deletion.
- **Cloud (18 playbooks)** has no dedicated container/Kubernetes playbook (pod escape, exposed kubelet/API server, malicious image pull) and no dedicated CI/CD-pipeline-compromise playbook (poisoned build step, stolen pipeline credentials, malicious dependency injection) — both are now common initial-access and lateral-movement paths in cloud-native environments and are currently only reachable indirectly through Credential Leakage (CLD-018) or Instance/VM Compromise (CLD-017).
- **Network (19 playbooks)** covers scanning, C2, and lateral movement well but has no playbook for on-path/ARP-spoofing attacks, rogue DHCP/wireless access points, or OT/ICS-protocol-specific anomalies — all plausible network-layer alert sources a mature SOC would expect a dedicated entry for.

### Playbooks that look like near-duplicates of each other

- **AI-009 RAG Poisoning** and **AI-010 Knowledge Base Poisoning** describe the same underlying attack pattern — a document an AI assistant trusts as authoritative gets tampered with, and the assistant then repeats the bad content to every user who asks a related question — differentiated only by whether the corpus is framed as a "retrieval index" or a "wiki/ITSM article." They currently read as two write-ups of one threat rather than two distinct threats; worth either merging or drawing an explicit, testable line between them (e.g., RAG Poisoning = the vector index itself is tampered post-ingestion; Knowledge Base Poisoning = the source document is tampered pre-ingestion) in a cross-reference note.
- **NW-009 Known Malicious IP Hit** and **NW-010 Known Malicious Domain Hit** run the identical workflow (match against a threat-intel feed → decide block-vs-investigate → determine if the connection was allowed or already blocked) and differ only in indicator type. These are strong candidates for merging into a single "Known Malicious Indicator Hit" playbook, or at minimum should cross-reference each other explicitly (they currently don't).
- **IAM-002 Brute Force**, **IAM-003 Password Spraying**, and **WEB-009 Password Spraying (Web-Facing)** all cover the same MITRE technique (T1110 / T1110.003) from three different angles — AD-integrated auth, a standalone AD-scoped spray writeup, and the web-facing/SaaS-login variant. IAM-002 already contains password spraying as a named sub-bullet, making IAM-003 largely redundant with it for on-prem AD targets; WEB-009 is legitimately distinct (different telemetry, different owner — Application Owner vs. Identity Team) and should stay separate, but IAM-002 and IAM-003 are worth consolidating or clearly scoping apart (e.g., IAM-002 = high-velocity/single-account brute force, IAM-003 = low-and-slow multi-account spray only).
