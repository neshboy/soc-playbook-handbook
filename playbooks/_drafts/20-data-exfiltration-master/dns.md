# DNS Exfiltration: Tunneling and Encoded Subdomain Queries

DNS gets abused for exfil for one boring reason: it's almost never blocked outbound, and most environments log it poorly or not at all. A workstation that can't reach 1.1.1.1 over HTTPS through the proxy can usually still send a DNS query to whatever resolver it's configured with — and if the attacker controls the authoritative nameserver for a domain, every query is a data delivery mechanism, not just a name lookup. Maps to **T1071.004 (Application Layer Protocol: DNS)**, and where the tooling wraps a full duplex tunnel over the query/response pairs, **T1572 (Protocol Tunneling)**. Broader bulk exfil over DNS as a side-channel to the "real" transfer protocol falls under **T1048 (Exfiltration Over Alternative Protocol)**; if a forwarder or internal relay is involved, consider **T1090 (Proxy)** too.

## Telemetry Sources

| Source | What it gives you | Common gap |
|---|---|---|
| Internal DNS server query logs (e.g., Windows DNS debug/analytical logging, BIND query log) | Client IP, queried FQDN, record type, timestamp | Often disabled by default — verbose logging has real perf cost, so many shops only turn it on after they already have a problem |
| Recursive resolver / DNS firewall logs (e.g., Infoblox, Cisco Umbrella, Quad9 for egress) | Aggregated query volume per client, NXDOMAIN rate, blocked/allowed verdicts | Retention windows are frequently short (7-30 days) relative to dwell time |
| Firewall/proxy egress logs, NetFlow | Confirms which host is actually talking to port 53/UDP externally (bypassing internal DNS) | NAT collapses multiple hosts to one logged IP without session correlation |
| Endpoint process telemetry (Security 4688, PowerShell 4104) | Process launching a tunneling client (`iodine.exe`, `dnscat2`, custom PowerShell) and the script block content if scripted | Command Line field on 4688 is empty unless command-line auditing is explicitly enabled |

## What the Indicators Actually Look Like

Legit DNS traffic is short-lived, low-cardinality per apex domain, and mostly resolves. Tunneling traffic inverts all three of those properties.

- **High subdomain cardinality against one apex domain.** A normal client resolves `www.example.com` a handful of times a day. A tunnel client generates a unique, high-entropy label on *every* query — `x7f2ke9dq1m.datastore-relay.net`, `a9k3lp02z.datastore-relay.net`, and so on — because the label itself carries the encoded payload chunk.
- **Label/FQDN length pressure.** DNS labels max out at 63 octets, FQDNs at 253. Tunneling tools chunk data to hug that ceiling — queries consistently in the 40-63 character label range are a strong tell versus the short, human-typed hostnames normal traffic produces.
- **Encoding signatures.** Base32 (case-insensitive alphabets, common because DNS is case-insensitive on the wire) or hex-encoded labels show up as long strings with flat character-frequency distribution — i.e., high Shannon entropy — versus dictionary-word-like legitimate hostnames.
- **NXDOMAIN-heavy behavior.** Some tunnel implementations don't care whether the query resolves; the authoritative server just needs to *see* the query to capture the encoded payload, so it returns NXDOMAIN or a throwaway A/TXT record. A client generating a sustained high NXDOMAIN ratio against a single domain is unusual outside of malware DGA activity.
- **Record type skew toward TXT/NULL/CNAME.** These types carry more payload per response than a bare A record, so tunneling tools favor them for the return channel.
- **Query volume asymmetry and cadence.** Bulk exfil over DNS shows bursty, sustained high query-per-minute counts from one host. Slow-drip tunneling (used to stay under volumetric alerting) shows a steady low-and-slow beacon interval over hours or days.
- **Newly registered or freshly re-pointed apex domains** as the exfil destination — cross-reference against domain age/WHOIS.

**[ANALYST]** - Pull the DNS query log for the source host, group by apex domain, and eyeball the subdomain set. Real question: are these labels human-readable service names, or do they look like they were generated by a hash function? Pair with 4688/4104 on the host to see what process actually issued the traffic — `powershell.exe` spawning from an Office process with a base64 script block is a very different case than a known DNS tunneling binary launched interactively. Don't assume every NXDOMAIN spike is malicious — broken split-horizon DNS and misconfigured internal search suffixes produce noisy false positives that look superficially similar.

**[ENGINEERING]** - Baseline query approach: per source IP, per rolling 1-hour window, count distinct subdomains against each registered apex domain, and flag when distinct-subdomain-count exceeds a threshold (tune per environment — start around 30-50 in an hour for a single workstation) **and** average label entropy on those subdomains exceeds a set bound (e.g., >3.5 bits/char). Layer in NXDOMAIN ratio >70% against that same apex as a second signal to cut noise from legitimate high-diversity SaaS subdomains (which usually resolve successfully).

```
// Pseudocode — DNS query log, KQL-style
DnsQueryLogs
| where TimeGenerated > ago(1h)
| extend ApexDomain = extract(@"([a-z0-9-]+\.[a-z]{2,})$", 1, QueryName)
| summarize DistinctSubdomains = dcount(QueryName),
            NxdomainRatio = countif(ResponseCode == "NXDOMAIN") * 1.0 / count(),
            AvgLabelLen = avg(strlen(tostring(split(QueryName, ".")[0])))
          by SourceIP, ApexDomain
| where DistinctSubdomains > 40 and NxdomainRatio > 0.7 and AvgLabelLen > 32
```

**[STAKEHOLDER]** - DNS exfil matters because it routes data through a protocol most network controls wave through unquestioned; a control gap here means sensitive data can leave even from segments with otherwise tight egress filtering. Closing it means enabling DNS logging and a query-pattern detector, not blocking DNS outright.

**[MANAGEMENT]** - Own by network/DNS engineering + detection engineering jointly; DNS query logging retention should target parity with the org's broader log retention SLA (commonly 90 days minimum for correlation with slow-drip campaigns). Review detection thresholds quarterly — CDN and SaaS subdomain patterns drift and will require re-tuning to hold false-positive rates down.

A confirmed DNS tunnel finding should feed the channel-narrowing step of the master exfil playbook directly — if DNS indicators are present, deprioritize HTTP/S and cloud-storage channels for that host pending correlation, but don't close them out until volume/timing analysis rules them in or out. Many DNS anomaly investigations end in Benign Positive (a misconfigured monitoring agent doing legitimate high-frequency health checks) or Insufficient Evidence (short retention window, log gap during the suspected window) — both are normal, valid closures, not investigation failures.
