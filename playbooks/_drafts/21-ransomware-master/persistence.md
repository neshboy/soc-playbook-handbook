# Persistence

*Ransomware Master Playbook — Attack Lifecycle: Persistence Stage*

## Why persistence looks thin in a ransomware timeline

Analysts coming from an APT background walk into a ransomware case expecting a rich persistence footprint — multiple scheduled tasks, several services, WMI subscriptions, registry Run keys stacked across every profile on the box. Then they pull the timeline and find almost nothing. One service. Maybe a Run key. Sometimes zero persistence at all outside the encryptor binary itself.

That's not a detection gap. It's the operating model. A ransomware affiliate's business case is speed to detonation, not long-term residency. Once the operator has domain admin, has staged the encryptor across enough hosts, and has (usually) already exfiltrated data for the extortion angle, there is no upside to surviving a reboot for weeks. Every extra persistence mechanism is another artifact for EDR to flag before detonation happens. Access brokers and initial-access crews build durable footholds; the ransomware affiliate that buys or inherits that access is optimizing for one loud event, not stealth over time. Treat "light persistence" as consistent with ransomware, not as evidence the intrusion is minor — it's often the opposite.

**[STAKEHOLDER]** - Minimal persistence means the attacker isn't planning to sit quietly and wait. If you've found the encryptor staged and a lone scheduled task or service, assume detonation is imminent or already triggered elsewhere, not that the incident is small.

## Service creation - 7045 (System log) and 4697 (Security log)

Ransomware crews frequently install a service to execute the encryptor with SYSTEM privileges across a fleet, or to disable/kill security tooling ahead of detonation (paired with T1562.001 Impair Defenses). 7045 is generated by the Service Control Manager and lands in the System log regardless of Security audit policy — it's often available even when Security-log auditing for object access is disabled or the log has been cleared. 4697 requires "Audit Security System Extension" success auditing to be enabled and lands in the Security log, correlated to the Subject that installed it.

| Field | 7045 (System) | 4697 (Security) |
|---|---|---|
| Log | System | Security |
| Requires audit policy | No | Yes |
| Service Name | Yes | Yes |
| Image Path / Service File Name | Yes | Yes |
| Start Type | Yes | Yes |
| Account context | Service account | Service account + Subject (who installed it) |

**[ANALYST]** - Baseline service creation on servers is not zero — patch management, backup agents, and monitoring tools install services constantly, so 7045/4697 alone is noisy. What separates ransomware-relevant hits: Image Path pointing at an unusual location (`C:\Windows\Temp`, `C:\ProgramData`, a UNC share, or a randomly-named binary in `C:\Users\<user>\AppData`), a service name that mimics a legitimate product but doesn't match the real vendor path, or a Start Type of "Demand"/manual paired with immediate invocation — because the crew only needs it to fire once. Cross-reference the Service File Name against Sysmon Event ID 1 (Process Creation) for the same host and near-identical timestamp; the hash and full command line there tell you far more than the SCM event alone. Also check whether the install coincides with a burst of Sysmon 23 (FileDelete) or 4697 entries disabling AV/EDR services — that pattern (kill switch service, then encryptor service) is common immediately pre-detonation.

**[ENGINEERING]** - Correlate on host + narrow time window rather than relying on 7045/4697 as a standalone high-fidelity alert; false-positive rate from legitimate software deployment is high without that join.

```
// Pseudocode - SIEM correlation, adapt to your query language
event.code in (7045, 4697)
| where ImagePath matches (".*\\Temp\\.*", ".*\\ProgramData\\.*", "\\\\\\\\.*\\\\.*\\.exe")
   or ImagePath !contains VendorPathAllowlist
| join kind=inner (
    Sysmon
    | where EventID == 1
) on Host, ImagePath ~= NewProcessName, timestamp within 2m
| project Host, ServiceName, ImagePath, ParentProcess, Hashes, Subject
```

Maps to **T1543.003** (Create or Modify System Process: Windows Service).

## Scheduled tasks - 4698

4698 records task creation with the full Task Content XML, including the `<Actions>` block with the literal command run. Ransomware use here is usually one of two patterns: a delayed/repeating trigger to relaunch the encryptor or a cleanup script (deleting shadow copies, log files) shortly after detonation, or a task created purely to survive an interrupted first attempt (host got isolated mid-encryption, task exists to resume on next logon/reboot).

**[ANALYST]** - Pull the Task Content XML directly, don't rely on Task Name alone — crews reuse legitimate-sounding names (`GoogleUpdateTaskMachineCore`, `OneDriveStandaloneUpdater`) that don't match the actual `<Command>`/`<Arguments>` inside. Check the Subject who created it against expected admin/deployment accounts, and check the trigger type: a one-time trigger a few minutes in the future is a very different signal than a recurring daily task.

Maps to **T1053.005** (Scheduled Task/Job: Scheduled Task).

## Registry Run keys - Sysmon 12/13/14

`HKCU\...\Run`, `HKLM\...\Run`, and RunOnce entries are cheap, fast to write, and don't require SCM overhead — appealing when the crew wants something that survives one reboot cycle without building a service. Sysmon Event ID 13 (RegistryEvent - value set) is the one you'll see most; 12 catches key creation, 14 catches renames.

**[ENGINEERING]** - Filter Sysmon 13 on `TargetObject` containing `\Run\`, `\RunOnce\`, or `\Winlogon\Shell` / `\Userinit`, then exclude your known software allowlist (updaters, VPN clients). What's left is a short, high-signal list on most endpoint fleets — Run key writes are far less common as noise than service installs.

```
EventID == 13
| where TargetObject matches (
    ".*\\Run\\.*", ".*\\RunOnce\\.*",
    ".*Winlogon\\\\Shell.*", ".*Winlogon\\\\Userinit.*")
| where Image !in (KnownGoodAllowlist)
| project Host, Image, TargetObject, Details, UtcTime
```

Maps to **T1547.001** (Boot or Logon Autostart Execution: Registry Run Keys).

**[MANAGEMENT]** - None of these three mechanisms alone justifies a P1 by itself, but any hit during an active ransomware engagement should auto-escalate rather than sit in a triage queue — by the time persistence lands, detonation is frequently hours away, not days. SOC leadership should pre-authorize analysts to isolate on high-confidence Run-key/service/task hits tied to an already-open ransomware case without waiting for a second approval loop; the SLA that matters here is minutes, not the standard severity-based response window.
